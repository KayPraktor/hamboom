# پشتیبان، بازیابی و migration در استقرار

> **M5 فاز ۷.** قاعده‌ی این فاز یک جمله است:
> ★★ **یک پشتیبانِ بازیابی‌نشده پشتیبان نیست.**
>
> پس این‌جا سه چیز هست که هر سه **اجرا می‌شوند**، نه اینکه نوشته شوند:
> پشتیبانِ دیتابیس، آینه‌ی Object Storage، و **مشقِ بازیابی** — که یک گیتِ واقعی است
> و در هر اجرای CI هم می‌آید.

| دستور | چه می‌کند | کِی |
|---|---|---|
| `pnpm infra:backup` | `pg_dump` → باکتِ **جدا** + مانیفست + راستی‌آزماییِ اندازه | شبانه |
| `pnpm infra:backup-storage` | آینه‌ی افزایشیِ `snapshots` و `assets` + مانیفستِ آن لحظه | شبانه |
| ★★ `pnpm infra:restore-drill` | پشتیبان را روی دیتابیسِ **خالی** برمی‌گرداند و پنج ادعا را می‌سنجد | هفتگی، و در CI |
| `pnpm infra:restore-drill -- --self-test` | چهار شکستنِ عمدی، هر کدام باید چکِ **درستش** را قرمز کند | در CI |

## چه چیزی پشتیبان می‌گیرد و چه چیزی **عمداً** نه

| داده | کجاست | پشتیبان |
|---|---|---|
| کاربر، تیم، بورد، پرداخت، فاکتور، اشتراک | PostgreSQL | ✅ `pg_dump -Fc` روزانه |
| بایت‌های سندِ بوردها (`board_snapshots`) | باکتِ `snapshots` | ✅ آینه‌ی افزایشی |
| تصویرها و فایل‌های کاربر | باکتِ `assets` | ✅ آینه‌ی افزایشی |
| حضور، مکان‌نما، pub/subِ خوشه | Redis | ⛔ **عمداً نه** — حالتِ گذراست |

⚠️ **چرا پشتیبانِ دیتابیس به‌تنهایی کافی نیست:** ردیفِ `board_snapshots` فقط
**اشاره‌گر** است. بازیابیِ کاملِ دیتابیس با باکتِ ازدست‌رفته یعنی بوردهایی که ردیف دارند
و محتوا ندارند — حالتی که **از نبودِ پشتیبان بدتر** است، چون سالم به‌نظر می‌رسد.

⛔ **از‌دست‌رفتنِ Redis یعنی کاربران یک بار دوباره وصل می‌شوند**، نه اینکه چیزی گم شود.
پشتیبان‌گرفتن از آن، پشتیبانی می‌سازد که هیچ‌وقت لازم نمی‌شود و در همان حال بزرگ می‌شود.

---

## ★★ باکتِ سوم، و چرا جداست

`S3_BUCKET_BACKUPS` عمداً **باکتِ سومی** است، نه یک پیشوند داخلِ `assets` (تصمیمِ
**M5-D7**):

> **یک دامنه‌ی خرابی برای داده و پشتیبانش یعنی هیچ پشتیبانی.** یک کلیدِ لو‌رفته، یک
> اسکریپتِ پاک‌سازیِ اشتباه، یا یک policyِ نادرست روی همان باکت، هم اصل را می‌بَرد هم
> نسخه‌ی پشتیبان را.

★ اگر سرویسِ ذخیره‌سازی اجازه می‌دهد، برای این باکت یک کلیدِ **فقط-نوشتن** بگیر: نودِ
production فقط باید بتواند بنویسد؛ خواندن کارِ روزِ بازیابی است.

## مانیفست: چرا کنارِ هر dump یک `.json` می‌نشیند

خودِ فایلِ dump **درباره‌ی خودش هیچ ادعای قابلِ‌سنجشی ندارد**. یک فایلِ ۳۰۰ کیلوبایتیِ
موفق‌آپلودشده از یک فایلِ ۳۰۰ کیلوبایتیِ **بریده** قابلِ تفکیک نیست، تا وقتی کسی
بازیابی‌اش کند. پس همان لحظه‌ی dump ثبت می‌شود:

```json
{
  "key": "pg/hamboom-2026-09-09T13-13-20Z.dump",
  "bytes": 301076,
  "sha256": "2788aeb2…",
  "serverVersion": "16.14",
  "migrations": { "0001_init.sql": "…", "…": "…" },
  "rows": { "boards": { "min": 60, "max": 60 }, "…": {} }
}
```

⚠️ **`rows` یک بازه است، نه یک عدد** — و این عمدی است. `pg_dump` snapshotش را از لحظه‌ای
وسطِ کار می‌گیرد؛ روی دیتابیسِ زنده شمارشِ «قبل» و «بعد» می‌توانند فرق کنند و هیچ‌کدام
تنهایی درست نیست. روی دیتابیسِ آرام بازه صفر-عرض است ⇒ برابریِ دقیق.

★ **و انتظاراتِ مشق از همین مانیفست می‌آید، نه از دیتابیسِ زنده** — وگرنه پشتیبانِ
سه‌شنبه با دیتابیسِ جمعه مقایسه می‌شد و هر بار «ناهم‌خوانی» می‌داد.

## ★★★ مشقِ بازیابی — پنج چک، و چرا یکی کافی نبود

**اندازه‌گیری‌ای که شکلِ این گیت را عوض کرد:** یک dumpِ واقعی عمداً بریده شد و
بازیابی‌اش امتحان شد. `pg_restore` با کدِ **۱** برگشت — ولی **هر ۳۱ جدول ساخته شده
بودند.** schema کامل، داده ناقص.

⇒ گیتی که فقط `db:fk-test` را روی نسخه‌ی بازیابی‌شده اجرا کند، روی همان پشتیبانِ ناقص
**سبز می‌شود**: آن تست ردیف‌های خودش را می‌سازد و rollback می‌کند و به داده‌ی موجود کاری
ندارد.

| # | چک | چه چیزی را می‌گیرد |
|---|---|---|
| ۱ | `sha256` با مانیفست | خرابیِ بایت‌ها بعد از آپلود |
| ۲ | کدِ خروجِ `pg_restore` | dumpِ بریده (دیسکِ پرشده حینِ پشتیبان) |
| ۳ | `schema_migrations` (نام + checksum) | بازیابی از نقطه‌ی زمانیِ اشتباه |
| ۴ | ★★ شمارشِ ردیفِ هر جدول در بازه | **داده‌ای که برنگشته** |
| ۵ | `db:fk-test` روی نسخه‌ی بازیابی‌شده | constraintها و رفتارِ واقعیِ CASCADE |

### خودآزمون: چهار شکستنِ عمدی، هرکدام برای یک چک

⚠️ صرفِ «قرمز شد» کافی نیست — چکی که هر شکستی را «اثبات» بشمارد، سبزِ دروغین است
(درسِ گیتِ ایمیج در فاز ۴). پس خودآزمون می‌سنجد **کدام** چک گرفتش:

| سناریو | انتظار | چکِ مسئول |
|---|---|---|
| پشتیبانِ سالم | **سبز** | — (وگرنه یک گیتِ «همیشه قرمز» هم پاس می‌شد) |
| یک بایتِ عوض‌شده | قرمز | ۱ |
| بریده، با مانیفستِ هماهنگ | قرمز | ۲ |
| ★★ داده‌ی **یک جدول** جا مانده | قرمز | **فقط ۴** — چهار چکِ دیگر سبز می‌مانند |
| `--schema-only` | قرمز | ۴ |

★★ سناریوی چهارم هسته‌ی گیت است: `pg_restore` کدِ **صفر** می‌دهد، ledger درست است،
`db:fk-test` **سبز** می‌شود — و یک جدول کامل از دست رفته.

⚠️ **و یک یافته‌ی خودِ خودآزمون:** انتظار این بود که در سناریوی `--schema-only` هم
`db:fk-test` سبز بمانَد. نماند — چون آن اسکریپت چکی دارد که `free`/`pro`/`team` باید
**فعال** باشند، یعنی به seedِ جدولِ `plans` تکیه می‌کند. پس اتفاقی یک چکِ داده هم هست،
ولی **فقط برای یک جدول**؛ خالی‌بودنِ `boards`/`payments` را نمی‌بیند.

### مشق به دیتابیسِ اصلی دست نمی‌زند

روی `<db>_restore_drill` بازیابی می‌کند و در پایان پاکش می‌کند (`--keep` برای بازرسیِ
دستی). اگر نامِ مشق با نامِ مبدأ یکی شود، **متوقف می‌شود**.

⚠️ `--self-test` یک ردیفِ سنتینل در `otp_challenges`ِ **مبدأ** می‌نویسد و پاکش می‌کند،
پس روی `APP_ENV=production` **اجرا نمی‌شود**. آن‌جا فقط خودِ مشق را بزن.

## ابزارِ `pg_dump` از کجا می‌آید

| حالت | کِی انتخاب می‌شود | چطور |
|---|---|---|
| `path` | باینری روی PATH هست (کانتینرِ production) | مستقیم با `-h/-p/-U` |
| `docker` | نیست، یا نسخه‌اش از سرور **قدیمی‌تر** است | `docker exec -i <کانتینر>` |

★ حالتِ انتخاب‌شده و **هر دو نسخه** در اولین خطِ خروجی چاپ می‌شوند. اگر کسی فکر کند
dumpِ production را گرفته ولی در واقع از کانتینرِ لوکال گرفته، بدترین نوعِ سبزِ دروغین
است.

⚠️ **کلاینتِ قدیمی‌تر از سرور خطاست** و کلاینتِ جلوتر هشدار می‌گیرد: خروجی‌اش ممکن است
نحوی داشته باشد که سرورِ قدیمی‌تر در **روزِ حادثه** نپذیرد.

★ ایمیجِ api کلاینتِ **۱۶** را دارد (پین‌شده و هم‌نسخه‌ی `postgres:16` در compose)؛
گیتِ `images` در CI همین را ادعا می‌کند و با انتظارِ اشتباه قرمز می‌شود.

## داستانِ migration در استقرار (گام ۷٫۳)

**چه کسی می‌زندش؟** هیچ‌کس. سرویسِ یک‌بارمصرفِ `migrate` در
[`docker-compose.prod.yml`](../infra/docker/docker-compose.prod.yml) — و `api` و
`realtime` با `service_completed_successfully` **تا موفق‌شدنش بالا نمی‌آیند**.

**اگر وسطش بیفتد؟** هر migration در **تراکنشِ خودش** اجرا می‌شود:

- migrationهای قبلی commit شده‌اند و در `schema_migrations` ثبت‌اند،
- آنکه شکست، **کامل** rollback شده — نه نصفه،
- کانتینر با کدِ غیرصفر می‌میرد ⇒ `api` اصلاً بالا نمی‌آید ⇒ **نسخه‌ی قبلی سرِ کار
  می‌مانَد** و کاربر schemaی نیمه‌کاره نمی‌بیند.
- اجرای بعدی از همان‌جا ادامه می‌دهد.

⚠️ **پس `CREATE INDEX CONCURRENTLY` در این ریپو ممنوع است** — داخلِ تراکنش کار نمی‌کند.
(امروز هیچ migrationـی ندارد؛ `0004` صریح نوشته‌اش.)

★★ **و از فاز ۷ یک advisory lock هم دارد** (`811_451_002`، همسایه‌ی کلیدِ آشتی‌دهی):
دو `migrate`ِ هم‌زمان — مثلاً یک `docker compose up` هم‌زمان با یک اجرای دستی — هر دو
`applied` را خالی می‌دیدند و همان فایل را اجرا می‌کردند. نتیجه‌اش **بی‌خطر** بود
(«relation already exists») ولی استقرار را می‌انداخت.

⚠️ قفل با **همپوشانیِ واقعی** سنجیده شد، نه با ادعا: یک نشستِ دیگر قفل را ۶ ثانیه نگه
داشت و `migrate` دقیقاً ۶ ثانیه صبر کرد و بعد موفق شد — در برابرِ **۲۳۳ms** وقتی رقیبی
نیست.

⚠️ `lock_timeout = 60s` عمدی است: انتظارِ بی‌پایان پشتِ یک migrateِ گیرکرده، از شکستِ
صریح بدتر است — استقرار بی‌صدا معلق می‌مانَد.

⚠️ **`0001` با گیتِ checksum منجمد است.** ویرایشِ یک migrationِ اجراشده خطاست؛ فایلِ
جدید با شماره‌ی بعدی بساز.

## روی VM (بدونِ ایمیجِ دوم — [ADR-062](../ARCHITECTURE_DECISIONS.md#adr-062))

```bash
C="docker compose -f infra/docker/docker-compose.prod.yml --env-file .env.production"

# شبانه (cronِ خودِ VM)
$C --profile ops run --rm backup node scripts/backup-db.ts --prune=14
# ⚠️ نه `run --rm backup -- --prune=14`: ایمیجِ پایه‌ی node آرگومانی را که با «-» شروع شود
#    به `node` می‌دهد و `--prune=14` را اسم فایل می‌گیرد (اثبات: «Cannot find module»).
#    فرمِ درست همیشه `node scripts/<اسکریپت> <پرچم‌ها>` است — همان‌طور که sweep/purge نوشته‌اند.
$C --profile ops run --rm backup-storage

# ★★ هفتگی — این تزئینی نیست
$C --profile ops run --rm restore-drill
```

⚠️ **`--prune` پیش‌فرض خاموش است.** حذفِ پشتیبان برگشت ندارد، پس عملِ آگاهانه‌ی اپراتور
است؛ بدونش اسکریپت فقط می‌گوید چند پشتیبان در باکت هست. و هرگز به پشتیبانی که همین الان
ساخته شد دست نمی‌زند.

### روزِ حادثه — بازیابیِ واقعی

```bash
# ۱. دیتابیسِ خالی، و مطمئن شو api بالا نیست
$C stop api realtime

# ۲. کدام پشتیبان؟ (مشق همیشه آخرین را می‌گیرد؛ برای قدیمی‌تر --key بده)
$C --profile ops run --rm restore-drill node scripts/restore-drill.ts --key=pg/hamboom-<زمان>.dump --keep

# ۳. اگر مشق سبز بود: **جابه‌جاییِ نام** — دیتابیسِ مشق (--keep) همان نسخه‌ی راستی‌آزمایی‌شده است
$C exec postgres sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "ALTER DATABASE hamboom RENAME TO hamboom_broken_'$(date +%Y%m%d%H%M)'; ALTER DATABASE hamboom_restore_drill RENAME TO hamboom;"'
$C up -d api realtime        # ✅ همین چهار گام روی استکِ productionِ لوکال اجرا شد (infra/RUNBOOK.md §۴)
```

★ ترتیب عمدی است: **اول مشق روی یک دیتابیسِ دورریختنی، بعد دیتابیسِ اصلی.** بازیابیِ
مستقیم روی اصل یعنی اگر پشتیبان خراب باشد، هم اصل رفته هم پشتیبان.

## ⚠️ سقفی که امروز واقعی است

پورتِ `ObjectStore` نه stream دارد نه کپیِ سمتِ سرور ([ADR-013](../ARCHITECTURE_DECISIONS.md#adr-013))،
پس هر شیء کامل در حافظه بارگذاری می‌شود. برای dumpِ ~۳۰۰KB و فایل‌های ≤۱۰MB امروز
بی‌اهمیت است؛ بالای ۵۱۲MB اسکریپت **هشدارِ صریح** می‌دهد. تغییرِ پورت به streaming کارِ
M6 است و در [`TODO-M5-infra.md`](../TODO-M5-infra.md) ثبت است — نه چیزی که بی‌صدا بماند.
