## ★★ اول این را بخوان — هفت چیزی که اگر M6 رعایت نکند بی‌صدا می‌شکند

۱. ★★ **هر مسیرِ apiِ تازه باید در [`api-prefixes.ts`](../apps/web/src/api-prefixes.ts) باشد و
   `pnpm infra:check-proxy -- --write` زده شود.** M6 مسیرهای `/admin/…` می‌سازد؛ بدونِ این،
   پروکسیِ dev و nginx هر دو به‌جای JSON **صفحه‌ی SPA** می‌دهند — و گیتِ `proxy` داخلِ `verify`
   قرمز می‌شود تا یادت بیاید. ⚠️ اگر `apps/admin` را روی **مبدأِ جدا** بگذاری، CORS و کوکیِ
   third-party می‌خوری؛ همان یک مبدأ، یک پیشوندِ تازه.
۲. ★★ **گاردهای بوت در `buildApp` هستند، نه در یک جای دیگر.** ماژولِ ادمین داخلِ `apps/api` از
   همان‌جا رد می‌شود؛ ولی اگر M6 سرورِ جدایی بالا بیاورد، باید خودش `assertProductionConfig` و
   گیتِ درگاه/پیامک را صدا بزند — همان درسی که M4 به M5 داد. و **`TRUST_PROXY`**: هر سرورِ
   HTTPای پشتِ nginx بدونِ آن **همه‌ی کاربران را یک IP** می‌بیند (اندازه‌گیری‌شده: ۴→۳→۲→۱).
۳. ★★ **هر میزبانِ خارجی در کدِ runtime، `verify` را قرمز می‌کند** ([`check-p2.ts`](../scripts/check-p2.ts)).
   پنلِ ادمین فونت، آیکون، نمودار — همه خودمیزبان. فهرستِ مجاز **دلیل‌دار** است و استثنای
   بی‌مصداق هم قرمز است؛ اضافه‌کردنِ یک میزبان یعنی یک ADR، نه یک خطِ allowlist.
۴. **`HB_ROOM_INFO` حالا keepalive هم هست** (گام ۹٫۱): هر ۲۵ ثانیه به هر اتاقِ دارای نشست —
   ساکت یا نه — تکرار می‌شود با **آخرین وضعیتِ راست‌گویانه**. هر مصرف‌کننده‌ی تازه‌ی این پیام باید idempotent باشد؛ و اگر
   `RT_HEARTBEAT_INTERVAL_MS` را عوض کردی، `silenceTimeoutMs`ِ ترابری (۷۵s = ۳×) را هم —
   `rt:reconnect` نامساوی را روی پیش‌فرض‌های واقعی assert می‌کند.
۵. **migrationها برگشت ندارند** و checksum دارند. Rollback = ایمیجِ قبلی + همان schema؛ migrationِ
   ناسازگار = بازیابیِ پشتیبان با از‌دست‌رفتنِ داده‌ی بعدش. پیش از هر استقرار پشتیبان
   ([`RUNBOOK`](../infra/RUNBOOK.md) §۲–۳).
۶. **`audit_logs` وجود دارد و هیچ‌کس در آن نمی‌نویسد.** M6 اولین نویسنده است (impersonation،
   تعلیق، verifyِ دستی). ⚠️ پیش از نوشتن، نگهداشتش را تصمیم بگیر — امروز هیچ purgeای آن را
   نمی‌بیند (گام ۸٫۴ عمداً کنارش گذاشت).
۷. **حذف همیشه دو گام است و هر دو صریح**: `infra:purge --delete` (ردیف‌ها، مرز = `TRASH_RETENTION_DAYS`)
   بعد `infra:sweep-orphans --delete` (بلاب‌ها). اگر پنلِ ادمین «حذفِ فوریِ حساب» می‌سازد، از
   همین دو رد شود — حذفِ ردیف بدونِ جاروب همان نشتیِ ثبت‌شده از M3 است.

## آنچه M6 مستقیماً تحویل می‌گیرد

### ۱. یک گپِ پشتیبان که باید بسته شود

`backup-storage` آینه‌ی **یک‌طرفه** می‌سازد و **بازیابیِ Object Storage اسکریپت ندارد**. این
جدی‌تر از «تصاویرِ آپلودی» است: بعد از فشرده‌سازی، updateهای پیش از snapshot از `board_updates`
حذف می‌شوند — محتوای بورد تا `seq_upto` فقط در snapshotِ Object Storage است. پشتیبانِ دیتابیس
بدونِ آینه بوردِ کامل را برنمی‌گرداند. ⇒ `infra:restore-storage` با همان انضباطِ مشق (کپی +
راستی‌آزماییِ اندازه/sha، خودآزمون با شکستنِ عمدی). ⊕ و پورتِ `ObjectStore` **stream ندارد**
(هر شیء کامل در حافظه؛ تنها هشدارِ اندازه ۵۱۲MB روی dumpِ `backup-db` است، `backup-storage`
هیچ هشداری ندارد) و `list`ش صفحه‌بندی ندارد — `sweep-orphans` همه‌ی کلیدها را در حافظه می‌گیرد
(هشدار بالای ۲۰۰هزار شیء). هر سه در همان پورت با هم حل می‌شوند.

### ۱٫۵ دو نقطه‌ی کورِ `/readyz` روی همین یک نود (یافته‌ی بازبینیِ runbook)

`/readyz` فقط دیتابیس را می‌سنجد. **Object Storageِ قطع** ⇒ بوردِ فشرده‌شده باز نمی‌شود (snapshot لازم
دارد)؛ **Redisِ قطع** ⇒ قفلِ صاحب fail-closed است و **هیچ نودی نمی‌نویسد** — updateها فقط در
حافظه‌ی realtime‌اند و ری‌استارتِ realtime پیش از بازگشتِ Redis **تنها مسیرِ از‌دست‌رفتنِ داده** روی
این استک است. هر دو با ۲۰۰ی readyz. ⚠️ سوالِ طراحی برای M6/M7: روی **یک** نود، قفلِ صاحب و
گذرگاهِ Redis اصلاً لازم‌اند؟ (`createRoomManager` بدونِ `ownerLock` صاحب را `true` می‌گیرد) —
یک `RT_CLUSTER=false` وابستگیِ Redis را از مسیرِ نوشتن برمی‌داشت؛ M2 است، ADR می‌خواهد.
و: **هیچ متریک/هشداری برای «سنِ آخرین پشتیبان» نیست** — cronِ RUNBOOK فقط فایلِ `FAILED` می‌نویسد.

### ۲. نودِ دوم — تریگرش اندازه‌پذیر است، پیش‌نیازش دو ذخیره‌ی مشترک

`hamboom_rt_adr048_trigger_ratio` ([`observability.md`](observability.md)) خودِ تریگرِ
[ADR-048](../ARCHITECTURE_DECISIONS.md#adr-048) است. پیش از نودِ دوم دو چیز باید از حافظه به
Redis بروند: `Idempotency-Key`ِ POSTهای غیرمالی (دو کلیکِ هم‌زمان ⇒ دو بورد) و سقفِ نرخِ api
(با N نود N برابر). جدولِ کامل در [`infra/README.md`](../infra/README.md).

### ۳. سه سوالِ زرین‌پال — همچنان پرسیده‌نشده

از M4 به ارث رسیده و چون حساب هنوز تایید نشده، همان‌طور مانده: بازه‌ی مجازِ verify پیش از
بازگشتِ خودکارِ پول (`BILLING_PENDING_EXPIRE_HOURS=72` حدس است) · رفتارِ `metadata.auto_verify` ·
بیشینه‌ی `ref_id`. و `ZarinpalGateway.listUnverified` هنوز با تماسِ زنده اثبات نشده
(`BILLING_ADOPT_ORPHANS` به همین دلیل خاموش).

## پیکربندیِ تازه‌ای که M5 در production گذاشت

```bash
IMAGE_TAG=<چاپِ infra:ship>        # حدس‌زدنش ممنوع
WEB_PORT=80 · WEB_TLS_PORT=443      # فقط web پورتِ هاست دارد

TRUST_PROXY=true                     # ★★ بدونش همه‌ی کاربران یک سطلِ نرخ دارند
SMS_PROVIDER=smsir + SMS_IR_*        # mock در production بالا نمی‌آید
S3_BUCKET_BACKUPS=hamboom-backups    # باکتِ **جدا** (M5-D7)
TRASH_RETENTION_DAYS=30              # M5-D9 — سیاست، نه تنظیم
RT_HEARTBEAT_INTERVAL_MS=25000       # جفت با silence ۷۵s در ترابری
BILLING_RECONCILE_ENABLED=true       # ⚠️ پیش‌فرضِ schema و compose هنوز false است (fail-safe)؛ فقط این فایل روشنش می‌کند
```

## ★★ درس‌های روشیِ M5 (گران‌ترین‌ها)

۱. ★★★ **بعضی نقص‌ها فقط با بالاآوردنِ استکِ واقعی پیدا می‌شوند — پنج بار در این ماژول.**
   `/assets`ِ Vite با پیشوندِ api (فاز ۲) · وابستگیِ اعلام‌نشده، **دو بار** (فاز ۱ و ۲؛ فقط نصبِ
   `--prod` داخلِ ایمیج نشانش داد) · استکِ mock که از فازِ ۴٫۵ بوت نمی‌شد (`SMS_IR_TEMPLATE_ID=""`)
   · و سقفِ نرخی که پشتِ nginx **سراسری** بود (۴۸ تستِ سبزِ api هیچ‌وقت پشتِ پروکسی اجرا نشده
   بودند). **«محلی سبز شد» برای CI و برای استک شرطِ لازم است، نه کافی.**
۲. ★★★ **اندازه بگیر، بعد تصمیم بگیر.** M5-D10 روی عددِ **غلطِ** ۱٫۲GB باز مانده بود؛ `docker save`ِ
   واقعی ۱۸۵MB بود و تصمیم برعکس شد ([ADR-063](../ARCHITECTURE_DECISIONS.md#adr-063)). و
   ۹٫۱: خواندنِ کد می‌گفت «کلاینت نگهبان ندارد» — ادعا بود تا رله‌ی سیاه‌چاله عددش را داد.
۳. ★★ **یک چک باید ادعای خودش را بسنجد.** مشقِ بازیابی با یک dumpِ عمداً بریده طراحی شد:
   `pg_restore` کدِ ۱ داد ولی هر ۳۱ جدول ساخته شده بود ⇒ فقط **شمارشِ ردیف** آن را می‌گرفت.
   و چکِ «گاردهای بوت» که هر شکستی را اثبات نمی‌شمارد **دو بار** CI را قرمز کرد (فاز ۴ و ۹٫۲)
   — هر دو بار درست.
۴. ★★ **گیتی که فقط دستی اجرا شود، اجرا نمی‌شود.** `db:smoke` ماه‌ها قرمز بود؛ `lint:css` هیچ‌وقت
   اجرا نشده بود؛ چهار خطِ سند از فاز ۷ (`run --rm backup -- --prune=14`) هرگز کار نکرده بود و
   فاز ۱۰ گرفتش. پس مشق، جاروب، P2 و سه حالتِ TLS همه **داخلِ CI**اند.
۵. ★★ **هر گیت با شکستنِ عمدی، و شکستن باید چکِ درستش را قرمز کند.** یک تستِ «از نو
   زمان‌بندی شد» با «زمان‌بندی نشد» یک شکل بود (هر دو یک تایمر) تا شناسه‌ی تایمر مقایسه شد.
۶. **عددِ سیاستی پیش‌فرض ندارد تا مالک بگوید؛ بعدش دقیقاً یک خانه دارد.** `purge` بدونِ `--days`
   بالا نمی‌آمد؛ با M5-D9 عدد به `TRASH_RETENTION_DAYS` رفت و `--days` فقط override شد.
۷. ⚠️ **تله‌های محیطیِ ماندگار** (تجربه‌ی sessionِ M5، جز اولی جایی در ریپو ثبت نیست): رنجِ
   excludedِ ویندوز (MinIO ۹۶۰۰→۱۵۹۰۰ در فاز ۷) · heredocِ bash در این محیط `\\n` را به خطِ نو
   تبدیل می‌کند — اسکریپتِ ویرایش را با Write بنویس، نه heredoc · `$PWD`ِ MSYS برای docker
   mount‌ناپذیر است · screenshot روی بومِ excalidraw time-out می‌کند.

## دستورهایی که M6 لازم دارد

```bash
pnpm verify                        # ★ تنها «سبز»ی که قابلِ استناد است (۱۵ گیت)
pnpm infra:check-proxy -- --write  # بعد از هر مسیرِ apiِ تازه (پیشوندِ /admin)
pnpm p2:check                      # میزبانِ خارجی در کدِ runtime؟ (داخلِ verify هم هست)
pnpm license:check                 # ⚠️ بدونِ --strict: تخلفِ P1 در devDependencies فقط **هشدار** است — apps/admin را دستی ببین
```
