# patches/ — اصلاحات جراحی روی پکیج‌های بالادست

> **پله‌ی B از [ADR-003](../ARCHITECTURE_DECISIONS.md#adr-003).**
>
> هر patch یک بدهی فنی است: با هر ارتقای نسخه‌ی پکیج ممکن است بشکند و باید
> دستی بازسازی شود. پس **هر patch باید در همین فایل ثبت شود** با چهار چیز:
> چه فایلی، چرا، اگر برداشته شود چه می‌شکند، و چطور تایید می‌کنیم که هنوز کار می‌کند.
>
> **معیار عبور به پله‌ی C (فورک کامل):** بیش از **۸ فایل** یا **۴۰۰ خط** patch.
> شمارش فعلی در جدول پایین.

## دستورات

```bash
pnpm patch @excalidraw/excalidraw@0.18.1   # ویرایش در پوشه‌ی موقت
pnpm patch-commit <path>                    # ثبت نهایی در patches/
```

نسخه‌ی پکیج **pin شده** است (`0.18.1` نه `^0.18.1`) چون patch ها به هش محتوای
نسخه گره می‌خورند. ارتقا باید یک تصمیم آگاهانه باشد، نه اثر جانبی `pnpm update`.

## patch های اعمال‌شده

| # | پکیج | فایل‌ها | خطوط | موضوع | ADR |
|---|---|---|---|---|---|
| — | — | ۰ | ۰ | هنوز هیچ patch ای اعمال نشده | — |

**جمع فعلی: ۰ فایل، ۰ خط** (آستانه: ۸ فایل / ۴۰۰ خط)

### P-1 — ست‌کردن `ctx.direction` قبل از `fillText` — **لازم نشد، پشتیبان می‌ماند**

مالک اعمال این patch را تایید کرده بود ([ADR-023](../ARCHITECTURE_DECISIONS.md#adr-023))،
ولی قبل از اعمالش یک راه بدون patch پیدا شد: wrap کردن
`CanvasRenderingContext2D.prototype.fillText` در زمان اجرا
([ADR-025](../ARCHITECTURE_DECISIONS.md#adr-025)).

**وضعیت: تایید شد که کار می‌کند** — شمارنده‌ی فراخوانی hook هنگام رندر واقعی
بوم بالا می‌رود (۳۸ فراخوانی در یک بار بارگذاری صفحه‌ی `#spike`). پس این patch
**اعمال نمی‌شود** و پروژه روی پله‌ی A می‌ماند.

متنش اینجا می‌ماند چون اگر نسخه‌ی بعدی موتور مسیر رندر را عوض کند (مثلاً به
worker یا OffscreenCanvas برود)، همین patch دوباره لازم می‌شود و نباید از صفر
کشفش کنیم.

**اگر لازم شد:** در `dist/prod/chunk-K2UTITRG.js` و `dist/dev/chunk-4FTI6OG3.js`،
درست قبل از حلقه‌ی `fillText` روی خطوط، مقدار `ctx.direction` از یک قلاب سراسری
خوانده شود تا منطق در کد ما بماند و patch یک‌خطی و بی‌منطق باقی بماند:

```js
globalThis.__hamboomTextDirection && (ctx.direction = globalThis.__hamboomTextDirection(text));
```

⚠️ هر دو build (`dev` و `prod`) باید patch شوند — Vite در حالت توسعه شرط
`development` را برمی‌دارد و فایل دیگری را لود می‌کند.

## مشکلات شناخته‌شده‌ی بالادست که **عمداً** patch نشده‌اند

این‌ها باگ واقعی‌اند ولی patch کردنشان الان ارزشش را ندارد. اینجا ثبت می‌شوند
تا فراموش نشوند و اگر روزی شدت‌شان بالا رفت، تصمیم دوباره گرفته شود.

### U-1 — پرش مکان‌نما بعد از نرمال‌سازی ورودی

- **پکیج:** `@excalidraw/excalidraw@0.18.1`
- **کجا:** `oninput` ویرایشگر inline (`.excalidraw-wysiwyg`)
- **شواهد:** [spike بخش ۹](../docs/spike-persian-text.md) — گام ۱٫۳ب

موتور روی هر `input` متن را نرمال می‌کند و بعد `selectionStart` **قبلی** را
برمی‌گرداند:

```js
d.oninput = () => {
  let F = normalize(d.value);
  if (d.value !== F) {
    let O = d.selectionStart;   // ← offset قدیمی خوانده می‌شود
    d.value = F;                //   طول رشته اینجا عوض می‌شود
    d.selectionStart = O;       // ← همان offset قدیمی برگردانده می‌شود
    d.selectionEnd = O;
  }
  o(d.value);
};
```

اگر نرمال‌سازی طول رشته را **قبل از** مکان‌نما عوض کند، مکان‌نما به جای منطقی
اشتباه می‌افتد.

**تنها محرک شناخته‌شده:** کاراکتر tab که به هشت فاصله باز می‌شود.

| ورودی | طول | مکان‌نما بعد | باید می‌بود |
|---|---|---|---|
| `خط\tاول` (فارسی) | ۶ → ۱۳ | ۳ | ۱۰ |
| `ab\tcd` (لاتین) | ۵ → ۱۲ | ۲ | ۹ |

**چرا الان patch نمی‌کنیم:**

1. **مسئله‌ی فارسی نیست.** شاهد لاتین دقیقاً همان انحراف را دارد. هیچ‌کدام از
   ۹ رشته‌ی دیگر آزمون (نیم‌فاصله، اعداد فارسی، اعراب، کشیده، RLM، emoji،
   ي/ك عربی) متن را عوض نمی‌کنند، پس مکان‌نما در آن‌ها درست می‌ماند.
2. **حالت لبه است.** tab در متن یک استیکی یا شکل، ورودی رایجی نیست.
3. **هر patch بدهی است.** patch کردن چیزی که در مسیر بحرانی نیست، فقط سطح
   تماس با کد بالادست را بی‌دلیل بزرگ می‌کند.

**اگر این شرایط عوض شد، دوباره تصمیم بگیر:**

- کاربران گزارش دادند که مکان‌نما می‌پرد
- محرک دیگری جز tab پیدا شد که در متن فارسی رایج است
- به‌هرحال داریم همان فایل را برای چیز دیگری patch می‌کنیم (هزینه‌ی حاشیه‌ای صفر)

**راه‌حل در صورت نیاز:** طول رشته را قبل و بعد مقایسه کن و offset را جابه‌جا کن:
`d.selectionStart = O + (F.length - previousValue.length)` — البته فقط وقتی تغییر
قبل از مکان‌نما رخ داده باشد، که نیاز به مقایسه‌ی prefix دارد.

## چک‌لیست ارتقای نسخه‌ی `@excalidraw/excalidraw`

هر بار که نسخه را بالا می‌بری:

1. `pnpm license:check` — نسخه‌ی جدید ممکن است وابستگی با لایسنس جدید بیاورد
2. همه‌ی patch های جدول بالا را دوباره اعمال کن و **خطای «patch اعمال نشد» را نادیده نگیر**
3. ★ **صفحه‌ی `#spike` را باز کن و شمارنده‌ی «فراخوانی hook» را ببین.**
   اگر روی **صفر** ماند یعنی موتور دیگر از `CanvasRenderingContext2D.prototype.fillText`
   رد نمی‌شود و [ADR-025](../ARCHITECTURE_DECISIONS.md#adr-025) شکسته — آن‌وقت
   باید P-1 بالا را اعمال کنی. این تنها راه تشخیص این رگرسیون است و بی‌صدا رخ می‌دهد.
4. `pnpm --filter @hamboom/canvas-core test` باید سبز بماند
4. صفحه‌های `#spike` و `#spike-edit` را دوباره اجرا کن و جدول‌ها را با
   [`docs/spike-persian-text.md`](../docs/spike-persian-text.md) مقایسه کن
5. بررسی کن مشکلات جدول U-* بالا در نسخه‌ی جدید رفع شده‌اند یا نه — اگر رفع شده،
   ورودی را از این فایل حذف کن
